# PDF Slide Extractor — 설계 문서

강의 슬라이드 형식 PDF의 **텍스트와 시각자료(다이어그램·표·박스)를 LLM Vision으로 종합해 자급자족 마크다운으로 변환**하는 웹 도구의 설계 문서입니다.

## 한 줄 정의

> 슬라이드 PDF의 각 페이지를 LLM Vision으로 분석해 **텍스트와 시각자료(다이어그램·표·박스·화살표)를 종합한 자급자족 마크다운**과 보조 참조 이미지를 ZIP으로 묶어 다운로드하는 개인/사내용 웹 도구.

**"종합 재처리" 출력**: 단순한 OCR이 아니라 다이어그램의 의미·박스의 관계·표의 데이터를 모두 텍스트로 풀어쓴 마크다운입니다. 이미지 없이 텍스트만 읽어도 슬라이드 학습 내용을 이해할 수 있어 RAG·파인튜닝·검색 인덱스 등 데이터 재처리에 바로 사용 가능합니다.

## 문제 정의

강의 자료(딥코 KDC 같은) PDF를 받아서 콘텐츠를 RAG·파인튜닝·검색 인덱스 등으로 재처리하려고 할 때:

- **텍스트 추출은 쉽지만** 슬라이드의 시각자료(다이어그램·표·박스·화살표)에 담긴 의미가 빠짐
- 다이어그램을 이미지로 떼어놓아도 LLM/검색기는 그 안의 의미를 못 읽음
- `pdfimages`는 벡터 그래픽 다이어그램을 못 뽑음 (PowerPoint로 그린 박스/화살표는 page content stream)
- 페이지를 통째로 캡처하면 제목·푸터·장식 일러스트까지 다 들어옴
- "이 페이지가 본문인지, 표지/구분 슬라이드인지" 자동 판별이 까다로움

이 도구는 **LLM Vision으로 페이지를 읽어 텍스트와 시각자료를 종합한 자급자족 마크다운**을 자동 생성합니다.

## 입력 / 출력

**입력**
- PDF 파일 1개 (슬라이드 형식, ~50페이지 이내 권장)

**출력 (ZIP)**
```
output.zip
├── content.md              # 슬라이드별 마크다운
└── images/
    ├── 06_데이터분석모델.png
    ├── 07_모델생성프로세스.png
    └── ...
```

`content.md` 안에서 다이어그램·표는 텍스트로 풀어쓰여 있고, 시각적 보조가 필요한 경우에만 이미지가 참조됩니다:

```markdown
## 슬라이드 7 — 데이터 분석 모델은 어떻게 만들어질까?

데이터 분석 모델은 다음 5단계를 거쳐 만들어집니다.

1. **데이터 수집** — 모델이 학습할 기반 정보를 모으는 단계
2. **데이터 전처리** — 수집한 데이터를 학습에 적합하도록 정제하는 과정
3. **모델 디자인** — 모델 구조를 설계하고 하이퍼파라미터를 설정하는 단계
4. **훈련 및 성능 평가** — 학습 데이터로 모델을 훈련시키고 성능을 점검·최적화
5. **모델 테스트** — 훈련에 사용되지 않은 데이터로 최종 성능 확인

## 핵심 단어

- **독립 변수**: 결과에 영향을 주는 원인 (예: 월, 요일, 시간)
- **종속 변수**: 그에 따라 바뀌는 결과 (예: 미세먼지 농도)

| 월 | 요일 | 시간 | 미세먼지 농도 |
|---|---|---|---|
| 4 | 0 | 2 | 35 |
| 6 | 1 | 3 | 42 |

![모델 생성 5단계 프로세스와 독립/종속 변수 예시](images/07_모델생성프로세스.png)
```

원본 슬라이드의 박스 다이어그램·표·라벨이 모두 마크다운에 녹아 있고, 이미지는 시각적 보조 역할입니다.

## 핵심 결정사항 요약

| 항목 | 선택 | 사유 |
|---|---|---|
| 출력 모드 | **종합 재처리** (시각자료 의미를 텍스트에 통합) | 데이터 재처리(RAG/파인튜닝) 용도 |
| 처리 구조 | **2-pass** (1패스: 강의 맥락 추출 → 2패스: 페이지별 상세) | 블록 코드/복잡 다이어그램에서 환각 감소 |
| 1패스 실패 처리 | **strict** (1패스 실패 = 작업 실패) | 결과 품질의 일관성 보장 |
| LLM | **3개 모델 사용자 선택**: Claude Haiku 4.5 / Gemini 2.5 Flash / Gemini 3 Flash | 비용·품질·도메인에 따라 사용자 선택 가능 |
| 어댑터 | `LLMProvider` Protocol로 모델별 SDK 차이 흡수 | Tool Use vs responseSchema 등을 한 인터페이스로 |
| 백엔드 | FastAPI | 파이썬 PDF 생태계와의 궁합 |
| 프론트 | Next.js (App Router) | SSR 불필요하지만 라우팅·DX가 깔끔 |
| 작업 큐 | Redis + RQ | Celery보다 가볍고 단일 노드에 충분 |
| 처리 모델 | 비동기 + 폴링 (1초 간격) | 28페이지 처리 ~3~5분 소요 |
| 배포 | docker-compose (로컬) | 개인/사내용, 인프라 미니멀 |
